Identidade & colaboradores

O Yggdrasil traz identidade e workforce embutidos. Você não precisa parafusar um IdP externo só para saber quem é quem dentro da plataforma: o core já modela os colaboradores do seu time interno, os times que eles formam e os grants que dizem o que cada time pode operar. Tudo versionado, auditável e dirigível pela CLI.

O modelo

Três aggregates compõem a identidade no yggdrasil-core. Eles vivem no Postgres do core e são o sujeito de toda decisão de autorização.

Collaborator
O sujeito interno canônico — uma pessoa do time de plataforma. Tem slug, display_name, primary_email, um status de ciclo de vida, um manager_id opcional, um primary_team_id e bolsos de dados estruturados: employment_data, personal_data, traits e third_party_identities. Cada escrita bem-sucedida bumpa um version (optimistic locking).
Team
O grupo que agrega colaboradores. Tem slug, name, type, status, um email canônico (que integrações podem usar para provisionar grupos externos) e um parent_team_id — times formam hierarquia. A ligação pessoa↔time é uma TeamMembership, com role, janela de validade (starts_at/ends_at) e source.
TeamGrant
O que dá poder. Cada grant liga um time a uma action de uma integration_instance (integration_instance_namespace + integration_instance_name + action_name; action_name: "*" é wildcard). É aqui que a autorização nasce: o usuário herda os grants dos seus times ativos.

A permissão efetiva de um colaborador não é um campo no seu registro — ela é derivada. O core resolve as actions yggdrasil:* que a pessoa pode executar a partir dos team_grants dos seus times ativos sobre a instância de gerenciamento do próprio Yggdrasil. Um grant wildcard (ou traits.yggdrasil_admin = true) significa acesso total.

Sessão & MFA

O login troca credenciais por um token de sessão. Você manda identifier (o slug ou e-mail do colaborador) e a senha; o core valida contra a senha local (Argon2id) e devolve um token. A sessão é uma linha persistida com expires_at, last_seen_at e estado de revogação — dá para listar e encerrar sessões individuais (aquele notebook esquecido no evento).

Para contas com MFA habilitado, o primeiro passo de login responde mfa_required com a lista de fatores. Aí você reenvia incluindo o segundo fator — um código TOTP do autenticador, ou um recovery code quando você não tem o app à mão. WebAuthn também é suportado como fator. Pela CLI:

login com MFA
$ yggdrasil login --server https://ygg.interno:9080 --username ana.silva
# a conta tem MFA: o core responde mfa_required (factors: totp)
$ yggdrasil login --server https://ygg.interno:9080 --username ana.silva --totp 492013
✓ logged in as ana.silva → context "ygg-interno" saved to ~/.yggdrasil/config.yaml

# sem o autenticador? use um recovery code:
$ yggdrasil login --server https://ygg.interno:9080 --username ana.silva --recovery-code 9f3a-2bd1-77ce

Em um terminal interativo, você pode omitir --server, --username e o código: a CLI pergunta. O login persiste um context nomeado em ~/.yggdrasil/config.yaml (estilo kubectl), e os comandos seguintes reusam aquele token.

Toda escrita carrega CSRF. A sessão emite um csrf_token derivado de forma determinística do id da sessão; surfaces espelham esse valor no header X-CSRF-Token em todo POST/PUT/PATCH/DELETE. O middleware recomputa o HMAC no servidor e rejeita divergências — defesa em profundidade sobre cookies SameSite=Strict.

Provedores de auth

Além da senha local, o core fala OAuth/OIDC com provedores externos (seu Google Workspace, um IdP corporativo, GitHub). Cada provedor é uma configuração core-owned: name, type (ex.: oidc), URLs de issuer/authorize/token, client_id e um client_secret_ref — você referencia o secret, nunca o inlina. Campos como auto_link_by_email e os *_field dizem ao core como mapear o perfil remoto para um colaborador.

Gerencie provedores pela CLI, como qualquer outro recurso declarativo:

auth providers
$ yggdrasil auth provider list
workspace-google        oidc       active

$ yggdrasil auth provider apply -f provider-google.yaml
✓ provider "workspace-google" applied
login URL: https://ygg.interno:9080/api/v1/auth/third-party/start/workspace-google

O manifesto de provider é direto — só os campos que o core conhece:

provider-google.yaml
name: "workspace-google"
type: "oidc"
status: "active"
display_name: "Google Workspace"
issuer_url: "https://accounts.google.com"
client_id: "1234.apps.googleusercontent.com"
client_secret_ref: "aws-sm://yggdrasil/google-oidc"  # referência, nunca o segredo
scopes: ["openid", "email", "profile"]
auto_link_by_email: true
email_field: "email"

Aplicado o provider, o fluxo de terceiros fica disponível em /api/v1/auth/third-party/start/<name> — a própria CLI imprime essa URL para você conferir na hora. Com auto_link_by_email, um login externo casa automaticamente com o colaborador de mesmo e-mail.

Ciclo de vida do colaborador

Pessoas entram, mudam de time, tiram férias, saem — e às vezes voltam. O yggdrasil collaborator cobre esse ciclo inteiro com verbos explícitos, cada um registrando um evento auditável no histórico do colaborador.

VerboO que faz
createCria o registro — --slug e --display-name obrigatórios; opcionais --email, --role, --manager, --team, --start-date.
get · listLê um colaborador (por id ou slug) ou lista todos (list --status <s>).
updatePatch de --display-name, --email ou --status.
offboardDesliga — --reason <voluntary|involuntary|contract-end|deceased>, com --end-date/--notice-days.
suspend · unsuspendSuspende e reativa o acesso temporariamente.
re-onboardReadmite quem voltou (--start-date, --role).
role-changeTroca o cargo (--new-role).
team-add · team-removeEntra/sai de um time (--team, opcional --role-in-team).
manager-changeReaponta o gestor (--new-manager, vazio para limpar).
attribute-setGrava um trait tipado (--key, --value, --type string|number|bool|json).
absence-start · absence-endRegistra ausência (--type vacation|leave-medical|leave-parental|leave-sabbatical).
lifecycle-eventsLê o histórico auditável do colaborador (--type, --limit).
provider-stateMostra como os provedores externos estão materializando aquela identidade.

Um onboarding típico encadeia poucos comandos — e o resto (provisionamento nos sistemas externos via integrações) reage ao estado:

onboarding
$ yggdrasil collaborator create --slug ana.silva --display-name "Ana Silva" \
    --email ana@interno --role platform-engineer --team team-infra
$ yggdrasil collaborator team-add ana.silva --team team-oncall --role-in-team responder
$ yggdrasil collaborator lifecycle-events ana.silva --limit 5

Identidade também é manifesto

Times e grants não vivem só na CLI imperativa: eles são kinds de manifesto (team, team_grant, team_role_binding), então você os declara, versiona e reconcilia como qualquer outro recurso. É GitOps para a sua própria força de trabalho.

A identidade aqui é o seu time interno de plataforma — quem opera o Yggdrasil — e não os usuários finais dos seus produtos. Veja Manifestos para o modelo declarativo de team/team_grant, e Workflows & runs para como uma mudança de identidade dispara provisionamento.
