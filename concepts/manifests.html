Manifestos

No Yggdrasil tudo é um manifesto versionado — um workflow, um tipo de integração, uma instância implantada, um time, a forma do próprio control plane. Você descreve o estado desejado como um documento declarativo, aplica, e o core guarda cada versão com histórico, checksum e a possibilidade de voltar atrás. É GitOps de verdade para a operação da sua plataforma.

O que é um manifesto

Um manifesto é um documento YAML (ou JSON) com a mesma forma que você reconhece do Kubernetes — de propósito, porque é o padrão que a maioria dos times já domina. O envelope tem quatro partes:

apiVersion
A versão do schema do envelope. Hoje: yggdrasil.io/v1alpha1. O core aceita múltiplas apiVersions durante janelas de depreciação.
kind
O tipo do recurso. Determina qual validador o core aplica ao spec (veja a lista abaixo). É normalizado para minúsculas antes de validar.
metadata
name (obrigatório), namespace (default global), description, labels e active. A tripla (kind, namespace, name) é a identidade lógica do recurso ao longo de todas as suas versões.
spec
O corpo específico do kind (obrigatório). É a única parte cujo formato muda de um kind para outro.

O modelo é declarativo: você não diz como chegar lá, diz qual é o estado desejado. O core reconcilia. Diferente do k8s, o Yggdrasil versiona toda escrita — cada apply com mudança gera uma nova versão, e o histórico fica consultável.

Os kinds

A lista autoritativa de kinds é o switch em manifest/validate.go no yggdrasil-core: cada kind aceito mapeia para uma função Validate…Spec. Estes são os tipos suportados hoje:

KindPara que serve
integration_familyContrato de interface (operações e schemas compartilhados) que muitos providers implementam.
integration_typeImplementação concreta de uma family (kubernetes, aws, github…), com seus reactors.
integration_instanceConfiguração implantada de um type — credenciais, cluster, projeto.
integration_quickstartManifesto voltado ao adotante: "instale isto com um comando", com inputs e steps.
productConjunto de integrações/workflows entregue como uma unidade.
workflowPipeline passo-a-passo de operações através das integrações.
workflow_templateBlueprint de workflow parametrizado, instanciado sob demanda.
surfaceConsole/painel interno que renderiza recortes da plataforma.
rbacPolítica de acesso sujeito-ação-recurso.
policyPolítica de runtime com condições (rate limit, residência de dados…).
resourceEntidade rastreada, originada do core ou descoberta numa integração (um bucket S3, um canal).
repository_bindingVínculo entre um repositório de origem e uma integração ou product.
guardian_policy / guardian_approval / guardian_memoryFluxo de aprovação e o seu histórico.
remediation_bundle / remediation_contractPeças do fluxo de resposta a incidentes.
control_planeDeclara a forma do deploy de produção (imagem, réplicas, Postgres, ingress, transportes).
tenantFronteira de tenancy para deploys multi-tenant.
ephemeral_environmentDefinição de ambiente efêmero (preview / ambientes de PR).

Um kind fora dessa lista é rejeitado com unsupported manifest kind — o core nunca persiste algo que não saiba validar.

Versionamento

Cada apply não sobrescreve nada: ele acrescenta uma versão. Ao receber um manifesto, o core:

  1. Normaliza e valida o envelope. Exige apiVersion, kind, metadata.name e spec não-vazio; faz trim/lowercase e aplica o validador do kind ao spec. Falha aqui devolve 422 — nada é gravado.
  2. Calcula o número da nova versão como MAX(version) + 1 dentro da tripla (kind, namespace, name). A primeira aplicação de um recurso é a versão 1.
  3. Promove a nova versão a ativa e desativa a anterior (active = FALSE) na mesma transação. Aplicar com metadata.active: false grava um "tombstone" sem deixar nenhuma versão ativa.
  4. Persiste um checksum SHA-256 determinístico do documento normalizado, para que aplicar de novo um conteúdo idêntico seja detectável (o diff reporta "sem mudanças").

Como toda versão antiga continua na tabela com seu spec intacto, o histórico é completo: você consulta qualquer versão por (kind, namespace, name, version) e nunca perde a forma anterior de um recurso.

Um manifesto na prática

Um integration_quickstart mínimo — o manifesto que torna uma integração instalável com um comando. Note o envelope (apiVersion + kind + metadata + spec) e como o spec carrega os campos específicos do kind:

slack-quickstart.yaml
apiVersion: yggdrasil.io/v1alpha1
kind: integration_quickstart
metadata:
  name: slack
  namespace: global
  description: "Conecte um workspace do Slack em um comando"
  labels:
    team: platform
spec:
  display_name: Slack
  providers:
    # cada provider vira um "instale isto" no console
    - id: slack-bot
      display_name: Slack Bot
      requires:
        - kind: integration_type
          name: slack
      inputs:
        - id: bot_token
          label: Bot token
          type: string
          required: true
          sensitive: true
      steps:
        - id: create-instance
          uses:
            kind: integration_instance
          with:
            token: "{{ .inputs.bot_token }}"

O ciclo de vida

Você dirige tudo pela CLI, que é fina: ela só molda a chamada HTTP para o core, que é a autoridade. O fluxo do dia a dia:

préviadiff / apply --dry-runo que mudaria
→
gravaapplynova versão ativa
→
lêget / describelista · YAML
→
desfazrollback / delete--to · --soft

Cada subcomando mapeia para uma operação no core. Note que rollback não é um endpoint dedicado: como toda versão guarda seu spec, voltar atrás é simplesmente reaplicar o spec da versão alvo como uma nova versão — o histórico nunca recua.

ciclo-de-vida
$ yggdrasil apply -f slack-quickstart.yaml --dry-run
~ integration_quickstart global/slack (dry-run, not applied)

$ yggdrasil apply -f slack-quickstart.yaml
created integration_quickstart global/slack (version 1)

$ yggdrasil get integration_quickstart -n global
KIND                     NAMESPACE  NAME   VERSION  ACTIVE
integration_quickstart   global     slack  1        true

$ yggdrasil describe integration_quickstart slack -n global   # imprime o manifesto em YAML

$ yggdrasil rollback integration_quickstart slack --to 1 --yes
✓ rolled back integration_quickstart global/slack to the contents of v1 (new version 3)

$ yggdrasil delete integration_quickstart slack --soft   # mantém o histórico, active=false

Flags reais que vale conhecer:

apply -f <arquivo> --dry-run
Mostra o diff contra a versão ativa sem gravar. -f - lê do stdin; vários documentos separados por --- num arquivo só.
diff -f <arquivo>
Compara o arquivo com o estado armazenado, sem aplicar.
get [<kind>] -n <ns> -o table|yaml|json --active-only
Lista ou busca manifestos. --active-only filtra só os ativos.
describe <kind> <name> -n <ns>
Imprime um manifesto como YAML.
rollback <kind> <name> --to <versão> -n <ns> --yes
Reaplica o spec da versão indicada como uma versão nova. --yes pula a confirmação.
delete <kind> <name> [--soft] -n <ns> --yes
--soft vira active=false em todas as versões, preservando o histórico; sem ele o delete é hard (remove todas as versões da identidade lógica), espelhando o default do core.
Manifestos são o quê; a execução é o como. Veja Workflows & runs para como um manifesto workflow vira execução, e Integrações para o modelo de quatro camadas (family → type → instance → provider).
O código é a fonte da verdade: a lista de kinds e as regras de versionamento vêm de manifest/validate.go, repository/manifest.go e model/manifest.go no yggdrasil-core.
