Início / Conceitos / CLI

CLI

Um único binário — yggdrasil — dirige o ciclo de vida inteiro do control plane: bootstrap, manifestos, runs, deploy, catálogo e colaboradores. Ele não reimplementa lógica de negócio: cada subcomando molda uma chamada HTTP para a API do yggdrasil-core, que é a autoridade sobre schema, versões e execução.

Filosofia

A CLI é deliberadamente fina. O servidor valida o manifesto, escreve a versão, despacha o workflow e aplica auth; a CLI só lê o arquivo, faz o POST e imprime a resposta. Isso a torna scriptável (qualquer comando roda em CI sem TUI, via flags), versionável (você guarda manifestos YAML no git e os aplica com apply) e auditável (toda ação vira uma chamada de API registrada no core).

Quase todo comando precisa de um contexto ativo: um yggdrasil-core para conversar. O contexto mora em ~/.yggdrasil/config.yaml — server, token e colaborador — no estilo kubectl. Você cria um com init ou login, troca com config use-context, e qualquer comando aceita --server/--token para sobrepor o contexto pontualmente.

Os comandos de workspace dev (integrations, surfaces) são a exceção: eles não falam com o core, e sim manipulam o checkout do monorepo. Todos os demais só precisam de um core acessível.

Referência de comandos

Os subcomandos se organizam pelo ciclo de vida da plataforma — do primeiro init até a construção dos seus próprios plugins.

Bootstrap & contexto

ComandoO que faz
init [--dir <path>]Bootstrap standalone em um comando: sobe Postgres, core e adapters via docker-compose. Com --server <url> apenas conecta a um yggdrasil-core já existente.
login --server <url> --username <slug>Troca credenciais por um token de sessão e salva um contexto. Para contas com MFA, passe --totp <código> ou --recovery-code <código> (em terminal interativo o código é pedido sozinho).
statusMostra o contexto ativo, o server alvo e um health-check (healthz/readyz) do core.
versionImprime a versão da CLI (e o hash de build, quando disponível).
updateBaixa e instala a release mais recente para o seu SO/arquitetura, verificando o checksum. --check só reporta.
config use-context <name>Troca o contexto de server ativo. A família config também tem get-contexts, current-context, set-context, delete-context e view.

Manifestos

ComandoO que faz
apply -f <file> [--dry-run]Cria uma nova versão do manifesto a partir de um arquivo (vários documentos separados por --- são suportados; -f - lê do stdin). Com --dry-run mostra o diff contra a versão ativa sem aplicar.
get <kind> [<name>]Lista todos os manifestos de um kind, ou busca um pelo nome. -o table|yaml|json escolhe o formato; -n escopa por namespace.
describe <kind> <name>Imprime um manifesto como YAML — atalho conveniente sobre o get … -o yaml.
diff -f <file>Compara, no cliente, os manifestos do arquivo contra as versões ativas no server, linha a linha.
delete <kind> <name> [--soft]Remove um manifesto (hard por padrão, pedindo confirmação). --soft apenas vira active=false e preserva o histórico.
rollback <kind> <name> --to <ver>Re-aplica o conteúdo de uma versão antiga como uma versão nova — o histórico fica intacto, então dá pra avançar de novo depois.

Runs

ComandoO que faz
run <workflow> [--input k=v] [--async]Dispara uma execução de workflow pelo nome. Síncrono por padrão (imprime o progresso passo a passo); --input k=v é repetível; --async devolve um run id na hora.
ops list | get | retry | abort | replayO lado operacional dos runs: ops list filtra e lista, ops get <run-id> inspeciona um run, e retry/abort/replay <run-id> gerenciam runs em andamento ou finalizados.
logs <run-id>Acompanha um run em tempo real, imprimindo as transições de status de cada passo até o estado terminal.

Control plane

ComandoO que faz
deploy control-plane -f cp.yamlAplica um manifesto control_plane e, em seguida, dispara o workflow de deploy contra ele — açúcar sobre apply + run com os defaults da topologia de bootstrap. --no-run aplica sem executar.

Colaboradores

ComandoO que faz
collaborator <verbo> [opts]Gerencia o ciclo de vida da força de trabalho. Verbos de ciclo: create, get, list, update, offboard, suspend, unsuspend, re-onboard. Mudanças de campo: role-change, team-add, team-remove, attribute-set, manager-change. Ausências: absence-start, absence-end. Auditoria: lifecycle-events, provider-state.

Auth

ComandoO que faz
auth provider listLista os provedores OAuth/OIDC configurados (nome, tipo, status).
auth provider apply -f <file>Registra ou atualiza um provedor a partir de YAML/JSON, e imprime a URL de login para verificar na hora. Também há auth provider get e delete.

Catálogo

ComandoO que faz
install <repo_ref>Instalação quickstart de uma integração em um yggdrasil-core remoto: busca o yggdrasil-quickstart.yaml do repo, guia pelos inputs declarados (TUI por padrão, --non-interactive para CI) e despacha. Aceita refs de GitHub (owner/repo[@ref][:path]) e de OCI (oci://…); --dry-run compila sem despachar.

Construir

ComandoO que faz
new integration <name> --owner <org>Faz o scaffold de um novo adapter de integração a partir do template oficial, reescrevendo os caminhos de módulo. O template compila de cara (go test ./...).
new surface <name> --owner <org>Faz o scaffold de uma nova surface (UI / edge). Flags compartilhadas: --module, --dir, --template, --no-git-init.

Dev de workspace

ComandoO que faz
integrations <subcomando>Helper para contribuidores que trabalham no monorepo: list, install, remove, installed e uma tui. Opera sobre o checkout local, não sobre um core remoto.
surfaces <subcomando>Helper irmão para surfaces no workspace: list, active, install, remove, installed, scaffold, activate, deactivate.

Auto-update

A CLI se mantém em dia sozinha. Depois de cada comando, ela checa o GitHub no máximo uma vez por intervalo (cacheando o resultado no config) e, se o binário estiver atrás, imprime uma dica discreta no stderr sugerindo yggdrasil update. O update baixa o artefato da release mais recente para o seu SO/arquitetura, confere o checksum contra o checksums.txt da release e troca o executável em uso de forma atômica. Builds de desenvolvimento nunca se sobrescrevem por engano — apenas reportam qual é a última release.

Uma sessão típica

Login com MFA, prévia do diff antes de aplicar, dispatch do workflow e inspeção do run:

terminal
$ yggdrasil login --server https://ygg.acme.internal --username gio --totp 481920
✓ logged in as gio → context "ygg-acme-internal" saved to ~/.yggdrasil/config.yaml

$ yggdrasil apply -f workflows/nightly-sync.yaml --dry-run
~ workflow global/nightly-sync (dry-run, not applied)
   schedule: "0 3 * * *"
+  retries: 3

$ yggdrasil apply -f workflows/nightly-sync.yaml
created workflow global/nightly-sync (version 7)

$ yggdrasil run nightly-sync --input target=staging --async
✓ dispatched global/nightly-sync (run r-2f9c, status running)
  follow: yggdrasil logs r-2f9c   |   yggdrasil ops get r-2f9c

$ yggdrasil ops get r-2f9c
run_id: r-2f9c
status: succeeded
workflow: nightly-sync
Sem nenhum contexto ainda? Comece por Self-hosting & primeiros passos: um yggdrasil init sobe o core e já grava seu primeiro contexto — depois é só status, apply e run.
