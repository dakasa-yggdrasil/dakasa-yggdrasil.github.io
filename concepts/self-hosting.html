Self-hosting & primeiros passos

Do zero a um control plane rodando na sua infra — em um comando. yggdrasil init sobe Postgres, o core e os adapters, cria o primeiro admin e salva um contexto da CLI. Você sai dele com um stack vivo e já autenticado, pronto para aplicar manifestos e rodar workflows.

Requisitos

O modo standalone empacota tudo em containers, então a lista é curta:

Docker
O engine precisa estar instalado e no PATH. O init aborta cedo com uma mensagem clara se não encontrar o binário docker.
Compose v2
O plugin docker compose (v2, com espaço — não o antigo docker-compose). O init valida rodando docker compose version antes de qualquer coisa.
A CLI yggdrasil
Um único binário estático, sem dependências de runtime. Instalação na próxima seção.
(opcional) um kubeconfig
O adapter de Kubernetes monta ~/.kube/config em modo somente-leitura. Só é necessário se você for usar workflows que aplicam objetos K8s.

Para o modo existing cluster (--server), você não precisa de Docker local nenhum — só de acesso de rede a um yggdrasil-core que já roda.

Instalar a CLI

A CLI é distribuída como binário pré-compilado nas GitHub Releases. Não há imagem de container: é um único binário estático por OS/arquitetura. Os arquivos seguem o padrão yggdrasil_<versão>_<os>_<arch>.tar.gz (Windows sai em .zip), com os e arch em minúsculas.

instalar a CLI
# escolha a release e seu OS/arch (minúsculos)
$ VERSION=0.1.0          # a release desejada
$ OS=darwin            # darwin | linux | windows
$ ARCH=arm64            # amd64 | arm64

$ curl -L -o yggdrasil.tar.gz \
    "https://github.com/dakasa-yggdrasil/yggdrasil/releases/download/v${VERSION}/yggdrasil_${VERSION}_${OS}_${ARCH}.tar.gz"
$ tar xzf yggdrasil.tar.gz
$ sudo mv yggdrasil /usr/local/bin/
$ yggdrasil version
✓ yggdrasil v0.1.0

Prefere compilar? go install github.com/dakasa-yggdrasil/yggdrasil/cmd/yggdrasil@latest (Go 1.25+) também funciona. E um binário de release sabe se atualizar sozinho: yggdrasil update baixa, verifica o checksum do goreleaser e troca o binário no lugar; yggdrasil update --check só reporta se há versão nova.

Subir standalone

Com Docker e a CLI no lugar, um comando põe o control plane inteiro de pé:

yggdrasil init
$ yggdrasil init
  escrevendo docker-compose.yml + .env em ./yggdrasil
  docker compose up -d …
  aguardando /readyz …

✓ yggdrasil is ready

  directory: /abs/path/yggdrasil
  server:    http://localhost:9080
  context:   local
  username:  admin
  password:  k3p…q9  (generated — save it now)

Por baixo, o init escreve um docker-compose.yml e um .env (com senhas aleatórias) no diretório alvo — ./yggdrasil por padrão, ajustável com --dir — roda docker compose up -d, faz polling em /readyz (que só responde quando o banco está alcançável e o bootstrap terminou), loga como admin e persiste o contexto em ~/.yggdrasil/config.yaml. A senha do admin é gerada aleatoriamente e impressa uma única vez ao final — anote-a. (Use --admin-username / --admin-password para fixar credenciais.)

O stack que sobe:

ServiçoPapelPorta
postgresEstado do core (manifestos versionados, runs, identidade)interna :5432
yggdrasil-coreO servidor com a autoridade — API HTTP /api/v1:9080 (host)
integration-kubernetesAdapter K8s (aplica objetos no seu cluster)adapter :8081 · health :8080
integration-schema-migrationsAdapter de migrações SQL (provider goose-postgres)adapter :8082 · health :8080

Só a porta do core (9080) é publicada no host por padrão; ela é configurável com --port. Confirme tudo com yggdrasil status.

Conectar a um core existente

Se você já subiu o yggdrasil-core por conta própria — Helm, Kustomize ou qualquer outro caminho — pule o compose inteiro e só registre o contexto. O init --server apenas faz o login e persiste a configuração:

core existente
# anexa a um core já rodando (sem Docker local)
$ yggdrasil init --server https://cp.example.com

# ou autentique uma conta a qualquer momento (suporta MFA)
$ yggdrasil login --server https://cp.example.com --username ops@example.com
  Authenticator code (TOTP): ••••••
✓ logged in as ops@example.com → context "cp-example-com" saved

O nome do contexto é derivado do host do servidor (para não sobrescrever o local do standalone), mas pode ser fixado com --context. Para contas com MFA, o login pede o código do autenticador automaticamente num terminal interativo; em CI, passe --totp <código> ou --recovery-code <código>. O config.yaml é multi-contexto no estilo kubectl: troque o ativo com a variável YGGDRASIL_CONTEXT.

Transporte: HTTP por padrão, AMQP opt-in

O core e os adapters conversam por um transporte. HTTP é o padrão e está sempre disponível — não há nada para configurar. RabbitMQ/AMQP é opt-in: o compose declara o RabbitMQ sob o profile amqp, então ele só sobe quando você pede explicitamente.

habilitar AMQP
# 1. no .env gerado, descomente as credenciais e a URL do broker
#    BROKER_URL=amqp://yggdrasil:…@rabbitmq:5672/

# 2. suba com o profile amqp ativo
$ docker compose --profile amqp up -d

Com BROKER_URL vazio, o core sobe em modo HTTP-only e o serviço RabbitMQ nem é iniciado. Você só liga o AMQP quando o volume de despacho justifica o broker.

Primeiro workflow

Com o stack de pé e o contexto salvo, o ciclo é sempre apply (cria uma nova versão do manifesto) seguido de run (despacha a execução). O run é síncrono por padrão e imprime o progresso passo a passo:

apply + run
$ yggdrasil apply -f my-workflow.yaml
✓ created workflow default/my-workflow (version 1)

$ yggdrasil run my-workflow -n default --input target=prod
workflow status: succeeded
  ✓ resolve-config                       succeeded
  ✓ apply-objects                        succeeded  (kubernetes.apply)
  ✓ verify                               succeeded

Passe --input k=v quantas vezes precisar; os valores vão como string e o schema do workflow coage o tipo no servidor. Quer só ver o diff antes de aplicar? yggdrasil apply -f … --dry-run. Quer dispatch assíncrono? yggdrasil run … --async devolve um run id para acompanhar com yggdrasil logs e yggdrasil ops get.

Deploy do control plane

Há um atalho dedicado para promover o próprio control plane: yggdrasil deploy control-plane aplica um manifesto control_plane e, em seguida, despacha o workflow seedado yggdrasil-deploy-control-plane contra ele — açúcar sintático sobre apply + run que já codifica os instances de Kubernetes e schema-migrations da topologia de bootstrap.

deploy control-plane
$ yggdrasil deploy control-plane -f cp.yaml
✓ applied control_plane global/yggdrasil
→ dispatching workflow yggdrasil-deploy-control-plane
workflow status: succeeded

Use --no-run para só aplicar o manifesto sem disparar o workflow, e -f - para ler de stdin. Os instances usados pelo deploy podem ser sobrescritos com --kubernetes-instance e --schema-migrations-instance.

Daqui, aprofunde no modelo declarativo em Manifestos, pluge seus sistemas via Integrações e exponha tudo internamente com Surfaces. Tudo continua rodando na sua infra.
