Workflows & runs

Um workflow é um manifesto: você declara, em ordem, os passos que uma intenção deve percorrer. Quando você o dispara, o core instancia um run — uma execução concreta, com estado, histórico passo a passo e um identificador para inspecionar. O workflow é a receita; o run é o prato que saiu do forno.

Anatomia de um workflow

O spec de um workflow tem quatro peças principais: um trigger (como ele pode ser iniciado — manual, schedule ou event), um input_schema (os inputs que ele aceita, com tipos e campos obrigatórios), defaults (valores aplicados quando o input não vem) e uma lista ordenada de steps.

Cada step tem um id, um bloco use que diz o que aquele passo dispara, e um with com os argumentos. O use.kind escolhe o tipo de passo:

integration
Despacha uma operação para uma integração. Você resolve o alvo por family + operation (resolução por contrato), ou fixa uma instância com instance_ref, ou desempata com provider_ref.
product
Roda uma operação de produto (materialize, installation.apply, installation.observe…) a partir de um with.product_ref.
yggdrasil
Executa em processo no próprio core, sem adapter — por exemplo apply_manifest para persistir um manifesto carregado em with.manifest.

Steps podem encadear: depends_on impõe ordem, condition decide se o passo roda (um passo cuja condição é falsa fica skipped), retry configura max_attempts/backoff_seconds, timeout_seconds limita a duração e for_each fan-out o passo sobre uma lista. Valores fluem entre passos por templates — {{ inputs.x }} e {{ steps.y.metadata.z }}.

deploy-service.yaml
trigger:
  mode: manual
dispatch_mode: async      # orçamento de tempo > timeout do gateway
input_schema:
  required: [image_repo, image_tag]
  properties:
    image_repo: { type: string, minLength: 1 }
    image_tag:  { type: string, minLength: 1 }
steps:
  - id: render-overrides
    use: { kind: yggdrasil, operation: control_plane.render }
    with:
      control_plane_ref: "payments-api"
  - id: apply
    depends_on: [render-overrides]
    use:
      kind: integration
      family: gitops
      operation: ensure_kustomize_source
    with:
      image_repo: "{{ inputs.image_repo }}"
      image_tag:  "{{ inputs.image_tag }}"
    retry: { max_attempts: 3, backoff_seconds: 10 }
    timeout_seconds: 180

Despachar um run

Você dispara um workflow pelo nome com yggdrasil run. Os inputs vão como pares --input chave=valor (repetível); os tipos são coagidos pelo input_schema no servidor, então a CLI sempre envia strings. Por padrão o run é síncrono — a CLI bloqueia e imprime o progresso passo a passo. Com --async, o core devolve um run id na hora e roda o workflow em segundo plano.

terminal
$ yggdrasil run deploy-service \
    --input image_repo=registry.example/payments-api \
    --input image_tag=v1.8.3
✓ render-overrides [succeeded] control_plane.render
✓ apply [succeeded] ensure_kustomize_source

$ yggdrasil run deploy-service --async \
    --input image_repo=registry.example/payments-api --input image_tag=v1.8.3
✓ dispatched global/deploy-service (run 9f3c…e21, status pending)
  follow: yggdrasil logs 9f3c…e21   |   yggdrasil ops get 9f3c…e21

Use -n/--namespace para mirar um namespace que não seja global. Workflows cujo orçamento de passos passa do timeout do gateway (≈30s) devem declarar dispatch_mode: async no manifesto, para que mesmo um run sem --async retorne um run id em vez de estourar o gateway.

Ciclo de vida de um run

Um run async nasce pending, passa a running quando a execução começa, e termina em um estado terminal — succeeded ou failed. Um run abortado vira cancelled. Esses são exatamente os estados que o registro workflow_runs aceita no core.

Dois detalhes úteis: o status committed é tratado como sucesso terminal (equivalente a succeeded); e a superfície de ops renomeia alguns estados na hora de exibir — pending vira scheduled, running vira active e cancelled vira aborted. Dentro de um run, cada step também tem seu próprio status: succeeded, failed ou skipped (quando a condition resolveu para falso).

Os filtros de ops list entendem tanto os nomes do banco quanto os exibidos: --status active casa com running, --status scheduled com pending e --status aborted com cancelled.

Inspecionar & gerenciar

A família yggdrasil ops é a visão operacional dos runs. logs faz o streaming de um run específico até ele terminar.

ops list
Lista runs. Filtros: --status (repetível), --integration, --search, --limit; saída -o table|json.
ops get <run-id>
Detalhe de um run — passos, resultados, erros. Saída -o yaml|json.
ops retry <run-id>
Reexecuta um run; aceita --reason para registrar a trilha de auditoria. Devolve um novo run id.
ops abort <run-id>
Marca um run em andamento como cancelled (exibido como aborted).
ops replay <run-id>
Reexecuta a partir de um run anterior, opcionalmente com novos inputs.
logs <run-id>
Acompanha as transições de status dos passos até o run chegar a um estado terminal — o mesmo feel de kubectl logs -f para um run pontual.
terminal
$ yggdrasil ops list --status active --integration gitops
RUN_ID    STATUS  WORKFLOW         INTEGRATION  TRIGGER
9f3c…e21  active  deploy-service   gitops       manual

$ yggdrasil logs 9f3c…e21
✓ render-overrides [succeeded] control_plane.render
→ apply [running] ensure_kustomize_source

$ yggdrasil ops retry 9f3c…e21 --reason "tag corrigida"
✓ retry 9f3c…e21 → new run 4b7a…c90

Reactors

Nem todo run é despachado à mão. Um reactor liga um evento do domínio a uma capacidade de integração: a declaração diz, em essência, "quando o evento X acontecer no core, chame a minha capacidade Y". Reactors são declarados no manifesto de um integration_type, num bloco reactors — cada entrada amarra um event_type (do catálogo canônico de eventos de ciclo de vida, como collaborator.created ou team_membership.added) a uma capability que precisa existir no action_catalog daquele tipo.

O mecanismo é desacoplado e durável. Quando um evento canônico é registrado, o core materializa uma reação pendente por integração interessada. Um dispatcher em segundo plano reivindica essas reações em lote e chama a capacidade do adapter, injetando um bloco _context com event_id e attempt para idempotência. Cada reação tem seu próprio ciclo: pending → in_progress → succeeded ou failed, e vai para dead_lettered depois de esgotar as tentativas.

Workflows com trigger.mode: event reagem ao mesmo fluxo de eventos por outro caminho: em vez de chamar uma capacidade de adapter, eles disparam um run inteiro quando eventos casam com os types e payload_filters declarados — com debounce para consolidar rajadas.
Os manifestos são o ponto de partida — um workflow é só mais um manifesto versionado. E quem realmente executa cada passo de tipo integration são os adapters: continue em Integrações para ver como uma capacidade vira uma chamada ao seu sistema.
