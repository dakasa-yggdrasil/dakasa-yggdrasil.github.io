Início / Conceitos / Surfaces

Surfaces

Surfaces são as bordas de UI internas do Yggdrasil — o painel pelo qual o time de plataforma enxerga e opera o control plane. É a janela para os operadores da empresa, não um frontend para o cliente final. Cada surface consome a API do core e não guarda estado de negócio próprio.

Escopo: IDP interno, não produto de end-user

Antes de qualquer coisa, a regra que define se algo é ou não uma surface do Yggdrasil. O Yggdrasil é a plataforma interna de engenharia (IDP) do time da empresa operadora — colaboradores, devops, engenheiros de plataforma. Ele administra recursos que são preocupação interna da companhia: setup de infra, configuração de integrações, auditoria, reconciliação dos próprios ativos.

Os serviços de backend da empresa, por outro lado, rodam operações para os end-users dela (clientes, consumidores): pagamentos, assinaturas, uploads de perfil. Uma surface vive sempre do lado do Yggdrasil dessa linha — é uma visão/despachante sobre o estado interno do IDP, nunca um app voltado ao cliente final.

A heurística de público (CLAUDE.md §0): se a audiência é o time interno da empresa vendo/gerenciando recursos da própria companhia → é surface do Yggdrasil. Se a audiência é o end-user do produto → não é surface, é o frontend de produto do operador. Um "dashboard de saúde de webhooks do Stripe" para o time de plataforma é uma surface; uma página "Pague sua fatura" para o cliente, não — mesmo que ela acabe despachando algum passo de infra pelo Yggdrasil.

O modelo slime

Se a integração é a espinha rígida do Yggdrasil (provisionamento idempotente, convenção de nomes estrita), a surface é a geleia que se molda em volta. A forma é deliberadamente livre: um dashboard, um wizard de onboarding, uma API REST/gRPC, um servidor MCP para ferramentas de LLM, um bot de Slack, um widget embutido em iframe — ou um híbrido de tudo isso. O que faz algo ser uma surface não é a forma, é o conjunto de invariantes abaixo.

A geleia também se adapta à pilha do operador, não o contrário: a surface não assume qual cloud a hospeda, qual CDN serve seus assets, nem qual framework de UI a constrói (React, Vue, Svelte, Go server-rendered — todos válidos). Esse é o princípio Lego aplicado às bordas.

Os invariantes

Mesmo a surface mais custom e estranha honra estes seis invariantes. Falhar em qualquer um significa que aquilo não é uma surface do Yggdrasil (pode ser um ótimo web app, mas não uma surface):

  1. Stateless quanto a estado de negócio — a surface não possui estado de negócio. Estado de UX no nível da sessão (rascunhos de formulário, painéis expandidos, cache de observação) é aceitável; o estado de negócio vive nas integrações e backends.
  2. Auth pela sessão do Yggdrasil (delegada) — nunca reimplemente login do zero. Surfaces públicas usam tokens read-only do Yggdrasil com escopo reduzido; as privadas usam a sessão completa.
  3. Backend-agnostic (via core) — chama /api/v1/* para ler dados e despacha workflows para mutações. Não fala direto com Stripe/AWS/GitHub — isso passa pelas integrações.
  4. Multi-tenant aware — respeita o escopo de integration_instance. O operador Acme vê os recursos da Acme; a DaKasa vê os da DaKasa. Visibilidade entre tenants exige uma concessão explícita de RBAC.
  5. Federável (deployable) — é um container/binário independente que pluga no console (ou roda standalone para variantes públicas). Não precisa do monorepo do Yggdrasil para compilar.
  6. Sem autoridade de negócio — a surface despacha, visualiza, compõe. Ela não decide regras de negócio ("quem cobrar", "quando reembolsar", "tem permissão para a ação X"). Essas decisões vivem nas integrações, nos workflows ou em backends com a devida autoridade.
O invariante 6 inclui autorização: a surface pode renderizar elementos de UI condicionalmente a partir das permissões da sessão, mas nunca pode assumir a ausência de uma verificação no servidor. A dica de permissão da surface é uma cortesia de UX, não uma fronteira de segurança — toda mutação despachada é autorizada server-side.

Console & design system

O console (surface-console) é a surface de referência: um SPA React 19 + Vite que renderiza a API do core para operadores humanos — colaboradores, times, integrações, workflows e identidade. Toda leitura e escrita passa por /api/v1/*; a sessão e toda a autoridade moram no core. Você pode forkar, reestilizar ou trocar o console inteiro por outra UI apontada para o mesmo core — a plataforma não muda.

O console agrega as demais surfaces, e cada integração pode publicar a sua própria (um painel por integração). O que mantém todas com a mesma cara é o surface-toolkit — o design system compartilhado em React. Ele entrega três coisas que toda surface precisa:

Tokens & tema

O SurfaceThemeProvider e os tokens (cores, espaçamento, tipografia) garantem que todas as surfaces compartilhem um único visual.

IntegrationAdminShell

O shell que cuida de roteamento, layout de abas, o seletor de instância e os estados de loading/vazio/erro — o autor só escreve o corpo das abas. Há também o TeamContextShell, centrado em time.

Hooks de dados

Hooks React Query (useYggdrasilAPI, useInstance, useDriftStatus, useSurfaceQuery…) que falam com o core pela sessão, mais abas prontas (DriftTab, IdentitiesTab, RecentRunsTab).

Todo hook passa por useYggdrasilAPI, que faz fetch com credentials: "include" contra a base /api/v1 — as surfaces nunca reimplementam auth, elas pegam carona na sessão delegada do Yggdrasil.

Criar a sua

O caminho recomendado é a CLI, que clona o surface-template (o scaffold canônico), descarta o histórico git, reescreve o caminho do módulo para github.com/<org>/surface-<nome> e roda git init. O resultado já compila e go test ./... passa.

scaffold de uma surface
$ yggdrasil new surface webhook-health --owner acme
✓ scaffold ready
  directory: ./surface-webhook-health
  module:    github.com/acme/surface-webhook-health
# o template compila out of the box; go test ./... passa

Se você trabalha dentro de um checkout do monorepo e quer a surface instalada sob surfaces/, há os helpers de workspace — e o subcomando surfaces gerencia o conjunto ativo:

yggdrasil surfaces
$ yggdrasil surfaces list                  # surfaces disponíveis no catálogo
$ yggdrasil surfaces scaffold webhook-health  # cria sob surfaces/
$ yggdrasil surfaces activate webhook-health  # adiciona ao compose ativo
$ yggdrasil surfaces active                # lista as ativas no momento

O scaffold registra um surface.manifest.json (kind: surface) que declara categoria, runtime, os core_contracts que a surface consome e suas capabilities — e serve /, /healthz e /readyz de saída. A partir daí você adiciona seus handlers (ou monta o IntegrationAdminShell do toolkit) e publica a imagem.

A lei completa de toda surface — o modelo slime, os seis invariantes, o que é fortemente desencorajado e o que é proibido — está no SURFACE_CONTRACT.md. Leia-o antes de qualquer mudança em uma surface. A forma é sua; os invariantes são o esqueleto da geleia.
