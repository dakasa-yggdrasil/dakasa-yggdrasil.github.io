Integrações

Uma integração é um adapter plugável: um worker independente que sabe falar com um sistema externo — Stripe, Grafana, AWS, GitHub — e o expõe ao Yggdrasil por um contrato explícito. Conecte tudo o que você opera e componha como peças de Lego: troque um provider sem reescrever o workflow que o usa.

O que um adapter faz (e o que não faz)

Um adapter é a camada declarativa de infraestrutura: ele reconcilia o estado de recursos externos (APIs de terceiros, sistemas, clouds) com o estado desejado que você expressa — garantindo idempotência, adoção de recursos pré-existentes e detecção de drift. Ele não carrega regra de negócio, não tem banco próprio e não assume qual cloud, cofre de segredos ou broker você usa.

A fronteira é nítida: o Yggdrasil cuida do que é responsabilidade interna da empresa (registrar o webhook do Stripe no painel, provisionar o bucket S3 dos assets, criar o repositório do time). Cobrar um cliente final ou guardar o pagamento dele é negócio — vive no backend, não aqui.

O modelo família → tipo → instância → provider

Quatro níveis organizam o catálogo de integrações. Entendê-los é metade da batalha:

família
O contrato compartilhado — o conjunto de operações que um ou mais providers implementam. Um repositório de adapter declara uma família (ex.: grafana) e a registra como autoridade sobre o vocabulário de capacidades.
integration_type
Uma implementação concreta da família, com seu Describe(), schemas e versão. Uma mesma família pode ter vários tipos: grafana-runtime (cliente HTTP contra um Grafana existente) e grafana-kubernetes (gerador da instalação) convivem sob a família grafana.
integration_instance
O tenant. Um tipo serve N instâncias, cada uma com credenciais isoladas: stripe-acme e stripe-corp são duas instâncias do tipo stripe, cada uma com sua própria API key e webhook secret. A instância é a unidade multi-tenant.
provider
O worker em execução — o pod do adapter (o binário Go) que de fato traduz capacidades em chamadas ao sistema externo. O campo Provider no Describe() identifica a família que ele atende.

O contrato Describe()

No boot, o core faz um handshake com cada adapter: pede o Describe() e valida o catálogo antes de despachar qualquer trabalho. Falhou o handshake, o adapter não fica elegível para execução. O Describe() publica tudo o que o core precisa saber: a versão, o transporte, os resource types, os schemas de credencial e instância (com metadados de UI que as surfaces consomem) e o catálogo de ações.

Abaixo, uma forma enxuta do Describe() do adapter stripe (AdapterVersion 2.4.0), derivada do spec.go real:

describe.stripe.yaml
provider: stripe
adapter:
  version: "2.4.0"
  transport: http_json          # RPC sobre HTTP
  timeout_seconds: 30
  endpoints:
    describe: /rpc/describe
    execute:  /rpc/execute
capabilities: [describe, execute]

credential_schema:             # segredos do tenant (nunca inline em manifesto)
  properties:
    stripe_api_key:
      type: string
      secret: true
      label: "Stripe API key"

instance_schema:               # config não-secreta por instância
  properties:
    stripe_webhook_secret: { type: string, secret: true }
    stripe_account_id:     { type: string }   # opcional: Stripe Connect

resource_types:                # recursos com identidade externa estável
  - name: customer
    canonical_prefix: thirdparty.stripe.customer
    default_actions: [ensure_customer, observe_customers, destroy_customer]
  - name: webhook_endpoint
    canonical_prefix: thirdparty.stripe.webhook_endpoint
    default_actions: [ensure_webhook_endpoint, observe_webhook_endpoints, destroy_webhook_endpoint]

Cada resource type tem um trio canônico: ensure_* (mutação idempotente que adota se já existe), observe_* (leitura, sem efeito) e destroy_* (remoção terminal — 404 do provider conta como sucesso). Há também discover_* (enumeração do lado do provider) e ações fora do trio na allowlist, como create_refund (movimento de dinheiro) e verify_webhook_signature (helper puro). Um linter (contractcheck) roda em CI e quebra o build se o Describe() divergir do que o Execute() realmente aceita.

Nomes CRUD (create_*, list_*, get_*, delete_*, update_*) para operações de recurso são proibidos — quebram a convenção. Renomeações antigas sobrevivem só como legacy aliases, resolvidos na borda do Execute() e removidos no próximo major.

Transportes

O core fala com o adapter por um dos dois transportes — declarados no Describe().adapter.transport e escolhidos pelo worker via a variável YGGDRASIL_TRANSPORT:

TransporteQuandoComo
http_json Padrão. YGGDRASIL_TRANSPORT ausente, http ou http_json. O worker faz ListenHTTP na ADAPTER_PORT (padrão 8081) e atende /rpc/describe + /rpc/execute. Um servidor de health separado roda na HEALTHCHECK_PORT (padrão 8080) com /healthz e /readyz.
rabbitmq / amqp Opt-in. YGGDRASIL_TRANSPORT=amqp (ou rabbitmq). O worker faz ListenAMQP contra a BROKER_URL (fatal se vazia) e consome das filas yggdrasil.adapter.<tipo>.describe e yggdrasil.adapter.<tipo>.execute.

O trabalho do adapter é o mesmo nos dois casos — o Describe() e o Execute() não sabem qual transporte os carregou. Pela mesma lógica Lego, o broker é uma escolha do operador: o adapter nunca abre conexão direta com um RabbitMQ hardcoded.

Instalar uma integração

O caminho rápido é yggdrasil install <repo_ref>. A CLI busca o yggdrasil-quickstart.yaml do repositório, conduz você pelos inputs declarados (TUI por padrão, ou --non-interactive para CI) e POSTa a instalação para o core, que compila o workflow que sobe o pod e registra a instância.

terminal
$ yggdrasil install dakasa-yggdrasil/integration-stripe
# pino uma versão
$ yggdrasil install dakasa-yggdrasil/integration-stripe@v2.4.0
# referência OCI (imagem do quickstart no registry)
$ yggdrasil install oci://ghcr.io/dakasa-yggdrasil/integration-stripe:v2.4.0
# CI: sem TUI, inputs por flag
$ yggdrasil install dakasa-yggdrasil/integration-grafana \
    --provider grafana-runtime --non-interactive \
    --input instance_name=grafana-prod --dry-run
✓ instalação compilada (--dry-run: não despachada)

O repo_ref aceita owner/repo, owner/repo@v1.2.3 (ref fixada), owner/repo:caminho.yaml (manifesto custom) e refs oci:// — última tag ou tag específica. Use --server/--token (ou o contexto ativo do seu login) para apontar o core; --dry-run pede ao servidor para compilar o workflow sem despachá-lo.

Criar a sua

Para escrever um novo adapter, comece pelo template oficial. A CLI clona dakasa-yggdrasil/integration-template, reescreve o módulo Go e o nome da integração, e deixa um esqueleto que já compila e passa nos testes:

terminal
$ yggdrasil new integration datadog --owner acme
✓ scaffold ready
  directory: ./integration-datadog
  module:    github.com/acme/integration-datadog
# edite internal/adapter/spec.go e adicione as suas operações
# adopters depois instalam com:
$ yggdrasil install acme/integration-datadog

O esqueleto traz o Describe()/Execute() em internal/adapter/spec.go, o linter de contrato, os health endpoints e o yggdrasil-quickstart.yaml de instalação já fiados. Os adapters usam o SDK Go (yggdrasil-sdk-go) para não reimplementar o encanamento de RPC: você constrói um adapter.New(...), registra os handlers describe/execute, escolhe o transporte (ListenHTTP ou ListenAMQP) e chama Run.

Ao desenhar capacidades, siga os prefixos canônicos. A pergunta-guia: o que estou manipulando tem identidade externa estável?

ensure_<recurso>
Mutação idempotente. O chamador diz "quero este estado"; o adapter faz GET-então-PUT internamente, adotando o recurso se já existir. Mesma entrada → mesma saída.
observe_<tipo>
Leitura, sem efeito colateral. Lista recursos, opcionalmente filtrados. Busca de um só item é filter={id:"..."} — não existe get_* separado.
destroy_<recurso>
Remoção terminal e idempotente. 404 do provider (já removido) conta como sucesso. Toda vez que você cria um ensure_*, entregue o destroy_* par no mesmo PR.

Toda mutação (ensure_* / destroy_*) emite um evento auditável (<provider>.<recurso>.ensured / .destroyed) — o SDK cuida disso por você quando você registra o reconciler. É o que separa "chamei a API por um wrapper" de "o Yggdrasil reconciliou o recurso e o mundo soube".

Leia o contrato canônico no integration-template (o INTEGRATION_CONTRACT.md é a lei) e o yggdrasil-sdk-go antes de tocar em qualquer adapter. Depois siga para Surfaces para ver como uma integração ganha sua própria UI interna.
